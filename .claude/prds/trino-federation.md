# PRD: trino-federation

## Executive Summary

A new `trino-federation` connector lets a single central Trino coordinator query a dataset that is
physically sharded across multiple regional Trino clusters. Each federated table is the logical
`UNION ALL` of the same table on every configured region (homogeneous shards). Queries issued
against the central catalog fan out to the regional clusters in parallel, and the connector pushes
predicates, projections, LIMIT/TopN, and — critically — aggregations down to each region so that
only pre-reduced results cross region boundaries.

## Problem Statement

Organizations keep data in-region for latency, cost, and data-residency reasons, but analysts and
BI tools need a single global view. Today the options are: replicate data centrally (expensive,
often prohibited), query each region separately and stitch results by hand (error-prone), or use a
generic JDBC-style connector per region and write manual `UNION ALL` SQL with no automatic
reduction (all raw rows cross the WAN). We need a connector where `SELECT region, sum(revenue)
FROM orders GROUP BY region` against the central cluster ships only a handful of pre-aggregated
rows from each region instead of the full fact table.

## User Stories

1. **Global analyst** — As an analyst, I query `federation.sales.orders` on the central Trino and
   get results spanning all regions without knowing how many regions exist.
   *Acceptance*: `SELECT count(*) FROM federation.sales.orders` returns the sum across all
   configured regional clusters; schema/table listing shows the union of homogeneous tables.
2. **Cost-conscious platform owner** — As a platform owner, I need aggregate queries to move only
   aggregated data across regions.
   *Acceptance*: For `SUM/COUNT/MIN/MAX/AVG` group-bys, each region executes a rewritten partial
   aggregate locally; `EXPLAIN` shows the aggregation pushed into the connector, and rows returned
   per region equal the number of local groups, not raw rows.
3. **Region-targeted user** — As a user debugging one region, I can filter by a synthetic
   `_region` column and the connector only contacts the matching region.
   *Acceptance*: `WHERE _region = 'us-east'` results in exactly one regional query (verifiable in
   regional query logs / connector metrics), and `_region` is selectable in results.
4. **BI tool** — As a BI client, filters, column pruning, LIMIT, and TopN generated by dashboards
   are executed inside each region.
   *Acceptance*: `WHERE`/`LIMIT`/`ORDER BY … LIMIT` clauses appear in the SQL that regions
   receive; projections restrict the regional SELECT list.
5. **Operator** — As an operator, I configure the catalog with a list of regions (name + URL +
   auth) and the remote catalog to expose; a failed region produces a clear, actionable error.
   *Acceptance*: catalog properties file with N regions works out of the box; unreachable region
   fails the query with an error naming the region.

## Functional Requirements

- New plugin `plugin/trino-federation`, catalog `connector.name=trino_federation`.
- Config: ordered list of regions, each with name, HTTP(S) URI of the regional Trino, and the
  remote catalog name to federate; shared settings for user/auth (static credentials in v1),
  connect/read timeouts, per-region schema/table listing.
- Metadata: schemas/tables/columns discovered from the first reachable region (homogeneous-shard
  assumption); schema drift between regions is detected at query time and fails with a clear error.
- Synthetic `VARCHAR _region` column on every table: selectable, and filterable such that region
  pruning skips non-matching regions entirely.
- Split generation: one split per participating region (after `_region` pruning); splits execute
  in parallel on central workers.
- Pushdown, applied per region:
  - Predicate pushdown (TupleDomain → SQL `WHERE`; supported types comparable across versions).
  - Projection/column pruning (dereference-free column subset in v1).
  - LIMIT pushdown (each region gets the LIMIT; central applies final LIMIT).
  - TopN pushdown (each region gets `ORDER BY … LIMIT n`; central does final TopN — guaranteed,
    not best-effort, at connector level marked as partial so engine re-sorts).
  - Aggregation pushdown with distributed rewrite: `count(*)`, `count(x)`, `sum`, `min`, `max`,
    `avg` (decomposed to `sum`+`count`), with `GROUP BY`, pushed as partial aggregates per region;
    the engine performs the final combine centrally. Unsupported aggregate shapes fall back to raw
    row shipping (correctness never sacrificed).
- Data transport: regional queries executed via the Trino client protocol
  (`io.trino:trino-client`), streaming results into pages; type mapping for the common scalar
  types (booleans, integers, decimals, floating point, varchar, varbinary, date, time(stamp)s).
- Runnable demo: extend the existing kind deployment with 1 central + 2 regional Trino clusters,
  regional shards of a TPC-H-derived dataset, central catalog wired to both regions, and a
  verification script demonstrating pushdown (row counts crossing regions).

## Non-Functional Requirements

- Regional queries for one central query run concurrently, not sequentially.
- No new external dependencies beyond what the repo already ships (`trino-client`, airlift http).
- Wire-compatible with regional clusters running the same Trino version (cross-version support is
  best-effort, not tested in v1).
- Follows repo conventions: airbase/airstyle clean, config classes with `@Config` + tests,
  `TrinoException` error codes, AssertJ tests.
- Documentation page under `docs/src/main/sphinx/connector/` and plugin registered in server
  packaging like other plugins.

## Success Criteria

- `DistributedQueryRunner`-based integration tests with ≥2 embedded regional Trinos pass,
  including correctness of unioned results, `_region` pruning, and each pushdown class.
- Pushdown verified mechanically in tests: aggregation/TopN/limit/predicate pushdown asserted via
  plan checks (`assertThat(query(...)).isFullyPushedDown()`-style or plan-pattern assertions) and
  via row-count-shipped metrics per region.
- `count(*)` over a table with R regions ships exactly R rows to the central cluster.
- Kind demo script stands up central + 2 regions and the verification queries pass.
- Full build (`./mvnw` for the new module) and `./mvnw validate` pass.

## Constraints & Assumptions

- Homogeneous shards: every region exposes the same remote catalog with identical table schemas;
  rows are disjoint by construction (the connector does not dedupe).
- Static catalog configuration; region list changes require catalog reload.
- v1 auth: username + optional password/basic auth over HTTPS or plain HTTP for demos; no OAuth
  pass-through.
- Read-only connector: no INSERT/CREATE/DELETE in v1.
- Central cluster and regions are assumed to run the same Trino version.

## Out of Scope

- Join pushdown across regions and co-located distributed joins.
- Write support (DML/DDL) of any kind.
- Per-region table name mapping / heterogeneous schemas.
- Cross-region deduplication or replica consistency handling.
- End-user identity propagation / impersonation to regions (v1 uses a fixed service identity).
- `approx_distinct`/HLL merge pushdown, `count(DISTINCT …)` pushdown, window functions.
- Cost-based region routing or statistics federation (beyond simple row-count passthrough if trivial).

## Dependencies

- `io.trino:trino-client` (in-repo) for the regional query protocol.
- Existing SPI pushdown hooks: `applyFilter`, `applyProjection`, `applyLimit`, `applyTopN`,
  `applyAggregation`.
- Existing kind demo assets from the `kubernetes-connector` epic for the demo environment.
- `trino-testing` (`DistributedQueryRunner`) for embedded multi-cluster tests.
