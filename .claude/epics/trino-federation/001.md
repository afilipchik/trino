# Task: Plugin skeleton, config, and registration

## Description

Create the `plugin/trino-federation` Maven module with the standard connector bootstrap:
`FederationPlugin`, `FederationConnectorFactory` (name `trino_federation`), `FederationConnector`,
Guice `FederationModule`, and `FederationConfig`. Register the module in the root `pom.xml` and in
`core/trino-server/src/main/provisio/trino.xml`. Model the pom and bootstrap on a lightweight
existing plugin (e.g. `trino-kubernetes` from the previous epic or `trino-loki`).

## Acceptance Criteria

- [ ] `./mvnw -pl plugin/trino-federation install -DskipTests` succeeds
- [ ] `FederationConfig` supports: `federation.regions` (ordered `name:uri` list or per-region
      keys), `federation.remote-catalog`, `federation.user`, `federation.password` (optional),
      `federation.connect-timeout`, `federation.request-timeout`
- [ ] Config class follows `.claude/rules` config-properties conventions; `TestFederationConfig`
      covers defaults + explicit mappings (airlift `ConfigAssertions`)
- [ ] Plugin registered in root pom `<modules>` and provisio `trino.xml`
- [ ] Connector instantiable via `TestingConnectorContext` smoke test

## Technical Details

- Dependencies in pom: `trino-spi` (provided), `trino-plugin-toolkit`, `trino-client`, airlift
  (bootstrap, configuration, json, units), guava, guice; test: `trino-testing`, assertj, junit 5.
- Read `.github/DEVELOPMENT.md` in full before writing Java (per CLAUDE.md).
- Region list parsing: prefer a simple comma list `name=uri,name=uri` into an ordered
  `List<RegionConfig>`; validate unique names, valid URIs.
