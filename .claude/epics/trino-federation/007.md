# Task: Aggregation pushdown with connector-side combine

## Description

The core data-movement win. Implement `applyAggregation` plus the fan-out combine execution path.
Because `PushAggregationIntoTableScan` only pushes `Step.SINGLE` and the engine does not
re-aggregate connector output, the connector must return final results: the aggregated table
handle produces a **single fan-out split** whose page source queries every active region
concurrently with the partial-aggregate SQL and combines regional partials in the connector.

## Acceptance Criteria

- [ ] `applyAggregation` accepts: `count(*)`, `count(x)`, `sum(x)` (integral, double, real,
      decimal), `min`/`max` (orderable pushable types), `avg` (double/real/decimal via sum+count
      decomposition), with 0..n grouping columns of pushable types
- [ ] Rejects (returns `Optional.empty()`): DISTINCT aggregates, filters/masks, ordered
      aggregates, other functions, unsupported argument types, grouping on `_region`… unless
      trivially supportable; rejection paths covered by fallback-correctness tests
- [ ] Single split per aggregated scan; page source fans out to all active regions on a bounded
      executor (config `federation.fanout-threads`, default = region count cap 16), streams
      partials, combines via hash table keyed on grouping values (`TypeOperators`-based equality/
      hash), emits final rows
- [ ] Combine functions: sum→sum (overflow semantics matching Trino), count→sum, min→min,
      max→max, avg→ divide combined sum by combined count at emit time with correct result type
      semantics (decimal avg only if exactly representable; otherwise reject at apply time)
- [ ] Empty-group semantics correct: global aggregation with all-empty regions returns the
      correct single row (`count=0`, `sum=NULL`, …)
- [ ] `count(*)` over 2 regions ships exactly 1 row per region (asserted via regional query text
      + shipped-row metrics)
- [ ] `EXPLAIN` shows aggregation absorbed into the table scan (plan assertion)

## Technical Details

- `AggregationApplicationResult`: output assignments are the final aggregate columns +
  (mapped) grouping columns; projections are plain `Variable` references; grouping column mapping
  provided so group-by symbols re-point at handle's aggregated columns.
- Handle's aggregation spec (built here, field reserved in task 004): grouping column handles +
  list of {remote partial expressions, combine kind, output type}.
- Memory: combine hash table bounded by pre-reduced input; report memory usage via page source
  `getMemoryUsage`; no spill in v1.
- Regional partial SQL comes from `RemoteSqlBuilder` aggregate support (task 003).
